# Data model

Schema changes are migration files only (see `CLAUDE.md`). Summary of what each migration adds:

- `20260913200000_house.sql` — `domains` (fixed ids = house window ids, bilingual jsonb copy, `target_seats`), `domain_relationships` (neighbour pairs, `a < b`), `seats` (status open/reserved/active/notice/closed), view `domain_staffing` (derived status: `needs` until active seats reach target). Public read on published domains and relationships; seats exposed only as counts through the view.
- `20260914090000_intake.sql` — `applications` (specialists), `contact_messages` (clients), `events` (first-party analytics), view `daily_domain_metrics`. Anon may **insert only**, with checks that internal fields (`status`, `handled_at`, `internal_note`, `decided_at`) arrive at defaults. Nobody can read these yet; that needs the role tables of phase 2.
- `20260916140000_people.sql` — `people` (one row per person, `user_id` to `auth.users` filled on first sign-in by email match, display name, lang), `organisations` (clients' companies), `memberships` (person × role enum `visitor|client|specialist|domain_lead|board|admin`, optional `domain_id` for specialist and domain lead, optional `organisation_id` for client, status `invited|active|revoked`). `seats.holder_person_id` now references `people`. Trigger `on_auth_user_created` links or creates the person. Security-definer helpers for policies: `current_person_id()`, `current_roles()`, `has_role(...)`, `has_domain_role(domain, ...)`, executable by `authenticated` only. RLS: a person reads and edits their own row and reads their own memberships; board and admin read everyone; only admin writes people, memberships and organisations. Nothing is readable by anon.
- `20260917080000_grants.sql` — explicit table privileges for anon, authenticated and service_role (preview branches carry no default privileges).
- `20260917100000_admin.sql` — `application_notes`, `audit_log` + `audit_row()` trigger on applications, application_notes, contact_messages, domains, seats, people, memberships, organisations (skips updates that only touch `updated_at`). Board/admin policies: read and update applications, contact_messages, domains (all rows), seats (insert, update, delete only when open/closed and empty); domain leads read their domain's applications. `20260917110000_audit_actor_fk.sql` adds the FK from `audit_log.actor_person_id` to people so the log page can embed the actor.
- `20260917130000_specialists.sql` — `specialist_profiles` (one per person, domain, slug, bilingual title/tagline/summary, skills jsonb, languages text[], rate, availability dates, links, portrait/cv paths, `is_published`), `experience`, `education`, `certifications`; helpers `owns_profile()`, `profile_is_live()`; definer view `specialist_teasers` (teaser columns of published profiles whose person holds an active seat in the domain). RLS: owner reads/edits own; board/admin all; clients read live ones. Board may create people, link accounts and grant `specialist` roles (the invite). Storage buckets `portraits` (public) and `cvs` (private) with owner-folder policies on `storage.objects`.
- `20260917150000_access_requests.sql` — `access_requests` (name, email, company, what they look for, `source_slug`, consent, status `received|approved|declined`, decided_at/by, internal note). Anon may insert with decision fields at defaults; board/admin read and update. Board may also grant `client` roles and insert organisations. `20260917160000_clients_read_specialists.sql` lets clients read the people rows of live specialists.
- `20260917180000_bookings.sql` — `booking_requests` (profile, requester, brief, duration 20/45, status `requested|accepted|proposed|declined|cancelled`, `first_reply_at`, `accepted_time_id`, `client_token`), `proposed_times` (by client or specialist), `booking_events` (each reply). Helpers `booking_is_mine()`, `booking_is_in_my_domain()`. Anyone inserts; specialists read/update their own; clients read their own; domain leads their domain; board/admin all. No anon reads: the requester's page goes through the service client with the token.
- `20260917210000_domain_depth.sql` — `domains.description` (i18n_text, paragraphs separated by a blank line) and `domains.typical_tasks` (jsonb `{da: [], en: []}`) for the domain page. The copy for all fifteen domains was drafted on 17 September 2026 and applied to the live project with targeted updates; Kim reviews it under Admin → Domæner.
- `supabase/seed.sql` — fifteen domains with DA/EN copy (name, tagline, blurb, window text, skills, description, typical briefs) and three open seats each. Idempotent upserts. No people: roles are granted at `/admin/personer` or with `pnpm roles` (see [runbooks/auth.md](../runbooks/auth.md)).
